## 4. 画像をリポジトリに入れる手順（ここを飛ばすと必ず壊れる）

このセッションからは **`git push` が使えない**（プロキシがリポジトリを許可していない）。
使えるのは GitHub MCP の `push_files` だけで、これは**テキストしか運べない**。

そのため画像は `site/assets/photo-src/` に base64 テキストとして置き、CI が復元する。

```
site/assets/photo-src/<name>.NN.b64   … 100文字×N行の base64
site/assets/photo-src/manifest.json   … チャンクごとのSHA-256／復元後のSHA-256／バイト数
tools/decode_photos.py                … 復元。1文字でも違えば「どのチャンクか」を名指しして失敗する
```

**この安全装置は飾りではない。** 今回 base64 を送った実測で、
24,000文字のチャンク15個のうち**5個が1文字化け、2個が丸ごと欠落**した。
Codex が入れた壊れた `komazawa-exterior.jpg`（7,470バイト）も同じ事故。

### 転送するときの手順（これを守れば1〜2回で通る）

1. 転写したものを**いったんローカルのスクラッチファイルに書く**
2. `git hash-object <scratch>` を実行し、元ファイルの blob SHA と一致するか確かめる
3. 違ったら `diff <(cat -n scratch) <(cat -n 元ファイル)` で行を特定して直す
4. **一致してから** `push_files` する
5. `get_file_contents` の `fields:["name","sha","size"]` で、載った blob SHA を確認する

補足：

- 1回の `push_files` に載る上限はおよそ **64KB**。72KB は切り詰められた。
- 大きなペイロードを送るメッセージには、**ツール呼び出しの前に文章を書かないこと**。
  書くと 6KB 付近で切り詰められる事例が出た。
- 複数エージェントを並列で走らせるときは、**スクラッチのパスをエージェントごとに分ける**。
  共有パスにすると互いに上書きし合う。

## 5. CI の並び順（ハマりどころ）

`.github/workflows/build-photos.yml` のステップ順には理由がある。

```
復元(decode) → ページ生成 → 退役アセットの撤去 → 状態をサマリに出力 → 画像検証 → コミット
```

**撤去を検証より先にやること。** 逆にすると、退役した壊れたJPEG（Codex の 7,470バイトの
`komazawa-exterior.jpg` など）が撤去される前に検証に引っかかり、ビルドが毎回止まる。
実際にこれで2回止まった。

もうひとつ：検証は `file -b | grep -qi jpeg` というシェルではなく `tools/verify_photos.py` に移した。
シェル版には (1) `.webp` が無いとグロブが展開されず落ちる (2) `grep -q` の SIGPIPE で
`pipefail` に引っかかる (3) 落ちても原因が分からない、という3つの問題があった。
今は何が見えて何が欠けているかを `$GITHUB_STEP_SUMMARY` に出すので、実行画面だけで分かる。
