## 1. 環境の制約（最重要・先に読む）

### 1-1. デプロイは main への push で自動的に走る

Cloudflare Workers Builds が GitHub に接続されており、**main に push するとおよそ30〜60秒後に本番へ反映**されます。
`wrangler deploy` を手で叩く必要はありません。

`wrangler.jsonc` の `assets.directory` が `./site` なので、**`site/` 配下がそのまま静的配信されます**。

### 1-2. Cowork 側からは git push できない（重要）

Cowork の実行環境は egress プロキシ越しで、このリポジトリが「セッションの許可リポジトリ」に入っていないため
`git push` も `api.github.com` への直接アクセスも **403 で拒否されます**。

そのため Cowork は **GitHub MCP（`create_or_update_file` / `push_files`）経由でのみ** コミットできます。
この API は本文を**テキストとして**受け取るので、

- テキストファイル（.py / .css / .html / .yml / .md）→ 問題なく push できる
- **バイナリ（.jpg / .webp / .png）→ 壊れる**

Codex 側で `git push` が通るなら、その制約はありません。**画像は Codex から直接 push するのが最短です。**

### 1-3. ネットワーク制限

Cowork の shell からは以下に到達できません（プロキシのポリシー拒否）。

- `trioland-social-publisher.mygate-jp.workers.dev`（本番。**WebFetch でのみ確認可能**）
- `drive.google.com` / `drive.usercontent.google.com`
- `api.github.com`

到達できるもの：`github.com`（git clone / fetch は可）、`raw.githubusercontent.com`。

本番の目視確認は WebFetch（テキスト取得のみ、画像は不可）に限られるため、
**レイアウト確認はローカルに `site/` を立てて Playwright で撮る**方法をとりました。

## 2. 写真まわりの根本原因（解決済み）

### 2-1. 壊れたJPEGがコミットされていた

`site/assets/` にあった以下が、**いずれもちょうど15,000バイト前後で切り詰められた壊れたファイル**でした。

| ファイル | サイズ | 状態 |
|---|---|---|
| `umegaoka.jpg` | 15,007 B | `broken data stream` |
| `child1.jpg` | 15,009 B | `image file is truncated` |
| `child2.jpg` | 15,054 B | `broken data stream` |
| `photos-v4.webp.b64` | 14,999 B | デコード不能 |
| `photos-b64-v2/` | 連結後も | デコード不能 |

原因は **1-2 のとおり、バイナリをテキストAPI経由でコミットしたこと**です。
これが本番 broken-image の直接の原因でした。すべて撤去済みです。

### 2-2. スプライトの座標定義が1つも無かった

旧実装は `.sprite-photo sp0`〜`sp11` で 1600x900 のスプライトから各コマを切り出す想定でしたが、
**`site.css` に `.sp0`〜`.sp11` の `background-position` が1行も定義されていませんでした**。
結果、全ての写真枠が同じ位置（左上）を表示していました。

さらに `photo-policy-v2.js` が、リポジトリに存在しない `/assets/umegaoka-hq.jpg` を HEAD で探し、
無ければ壊れた `/assets/umegaoka.jpg` にフォールバックしていました。

**撤去したもの**：`photo-loader.js` / `photo-policy-v2.js` / `photos-b64-v2/` / `photos-v4.webp.b64` /
`photos.jpg` / `photos-v2.jpg` / `.sprite-photo` クラス全般 / 各種マーカー .txt

### 2-3. img が縦に引き伸ばされていた

`.hero-media img` などに `width:100%` だけ指定され `height:auto` が無かったため、
HTML の `height` 属性がそのまま使われ、写真が歪んでいました。修正済み（`e66a4d4`）。

## 3. 現在の構成

```
build_site.py                    全ページHTML / robots.txt / sitemap.xml を生成（ここを編集する）
tools/build_photos.py            site/assets/photos/*.jpg を生成（低解像度スプライト由来・暫定）
site/assets/photos-b64-v5/*.txt  暫定素材の生成元（base64テキスト）
site/assets/photos/*.jpg         生成された写真（CIがコミット）
site/assets/site.css             スタイル（手で編集する唯一のCSS）
site/*.html                      生成物。直接編集しない（次のビルドで上書きされる）
site/recruit/*.html              求人SEO記事14本（インラインCSS・生成対象外・手書き）
docs/SITE.md                     写真運用と再発防止のルール
```

**ページを直すときは `build_site.py` を編集して `python3 build_site.py`。**
`site/*.html` を直接編集しても次のビルドで消えます。

### ワークフロー

| ファイル | name | 役割 | 起動条件 |
|---|---|---|---|
| `build-photos.yml` | Build site | HTMLと写真を生成してコミット＋旧アセット撤去 | main への push（`build_site.py` / `tools/` / `photos-b64-v5/` / 自身） |
| `site-smoke.yml` | Trioland site smoke | 本番の疎通＋**全画像の完全デコード検査** | Build site の完了後 |
| `sync-site-images.yml` | Sync site photos from Drive | Drive の元写真から高解像度版を生成 | 自身への push、手動 |

`site-smoke.yml` の画像デコード検査は**切り詰めJPEG再発防止のためのものです。消さないでください。**

### ⚠️ sitemap の落とし穴

`sitemap.xml` は `build_site.py` の `COLUMNS` から生成されます。
`site/recruit/` に記事を足したら、**必ず `COLUMNS` にも追加**してください。
忘れると次のビルドで sitemap から消えます（実際に一度発生しかけ、`093c132` で回収しました）。
