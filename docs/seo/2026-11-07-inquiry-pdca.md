## 1. 成果の定義

最上位は「外部から実際に受け付けた問い合わせ・見学申込・利用相談・採用応募」。会社/保育/放デイ、サービス利用/採用、根拠がある事業区分で分ける。内部検証、重複、スパムは実際の識別根拠があるものだけ除外する。問い合わせは契約・入園・入職とは違う。

評価経路：検索表示 → 検索クリック → 施設/サービス閲覧 → 相談CTA → 入力開始 → サーバー受付成功 → 外部有効問い合わせ。
GA4の `inquiry_submit_success` は外部有効問い合わせと未照合なら、そのイベント名と回数だけを表示。クリックは電話/LINE/採用/利用相談などを区別する。GA4とGSCは集計系が異なるため、そのまま同一母集団の段階率にしない。率の分子・分母と対象期間を明示する。

## 3. 初回サイクル：優先順位と担当

### P0 / MEAS-01：何を数えているかを確定（Codex）

目的：行なし・CTA・成功イベントを実問い合わせと誤認しない。
作業：
1. 既存site-smokeの最新結果・公開HTML・許可されたブラウザ確認経路を再利用し、放デイでタグがロードされるか、`trioTrack` が動くかを確認。問い合わせ実送信はしない。
2. `tools/trio_ga4.py`、フォームコード、`src/inquiry.js` の成功/失敗条件を調査。既存イベントの `cta_type` / `form_type` がGA4・Windsorのスキーマで読めるかを実際に確認。読み取れないこととイベント未発火を区別する。新しい個人データ項目を作らない。
3. 既存の許可済み読取専用受付集計から、ホスト・日付・受付区分・テスト判定の集計だけを照合する。生の相談内容や連絡先を取得/掲載しない。取得経路がなければ実装箇所と必要最小限の条件を記録し、再ログインや新規契約を推測で要求しない。
4. テストはローカル/ステージングのモックで行う。本番に架空の成功イベントを流さない。内部と外部の混入状況を確認。
完了条件：本番の計測状態、イベント定義、受付集計との照合可否、原因未確定範囲を証拠付きで明示。0件の定義が成立しない場合は未取得のまま。

### P1 / AS-01：既存施設ページから保護者の相談へ（Cowork提案→Codex実装）

対象：`/lopp.html`、`/compass.html`、`/availability.html`、対応する `afterschool/build_site.py`。まず1つの施設ページに絞って変更し、同時に複数の仮説を混ぜない。
Cowork：既存ページをスマホ幅で確認し、「どこにあるか・送迎を相談できるか・どんな支援か・見学の相談方法」の既存の事実を整理。キャッチだけでなく、地域/駅名と相談導線が分かる順番・文言の具体案を作成。タイトル/説明文はページ別実績と本文の一致を確認。声・実績・空き枠を捏造しない。
Codex：既存のfacility/kindクエリ処理があるか確認し、施設→利用相談フォームで施設・目的を保持できる場合は保持。CTAの文言と到達先を一致させ、送信先や必須項目は変えない。生成元に反映し、再生成で消えないこと、#formへ到達可能であること、採用用導線が残ることを検証。
主指標：対象施設の外部有効利用/見学問い合わせ件数。副指標：施設ページ閲覧、利用相談CTA、入力開始（同一期間・同一定義・計測の正常性確認が前提）。
基準期間：GA4が正しく取得できた完全日を実装前に固定。11/03は計測開始の部分日、11/06行なしは0扱いしない。
判定：公開確認日をD0としD+7/D+14。SEOのタイトル変更はD+28も評価。公開確認前に検証期間を開始しない。数が少ない段階で成功と断定しない。

### P2 / AS-02：入力負担の検証（P1と同時に同一箇所を変えない）

現状の学校名・学年等の必須項目が、空き確認/見学相談段階に必要かを、受付仕様と業務資料で確認。初期相談に必要な項目と利用決定後に必要な項目を整理した案をCoworkが提出。必須項目削除・問い合わせ区分追加・通知先変更は承認済み業務範囲を確認するまで実行しない。
コードで確かめられる入力チェックの不具合、スマホの操作不能、誤ったリンクは根拠付きで修正。原因が文言なのか必須項目なのかは未確定のまま扱う。

## 4. 進行管理

各施策に次を残す：ID、仮説、根拠、基準期間/実数、対象URL、実変更、担当、main/CI/本番、受信確認、公開確認日、D+7/D+14/D+28、結果、母数、継続/修正/停止。
有効な改善を毎回1件以上試みるが、件数達成のためだけに変更しない。コード不具合は判定日を待たず修正。安全に実行できない場合も、調査した段階・原因・代替経路・次の実行条件を記録する。

Coworkはまず本書の該当作業について既存引き継ぎとの重複を確認してから受領/着手を明示し、提案を `docs/seo/2026-11-07-cowork-inquiry-review.md` に保存する。Codexは提案の受領状況と実装・公開を証拠で追う。ファイル保存だけで相手が実行したとは言わない。既存Issue #15に本台帳の参照と状態を追記し、課題を乱立させない。

会社HP・保育HPにも同じ考え方を適用する。採用記事量産はせず、給与誤情報/壊れた導線の修正は継続。記事削除・301・canonical変更は流入/インデックス/内部リンクの検証後のみ。

## 5. 安全条件

新規課金/権限拡大、アクセス制限迂回、D1書き込み、公開問い合わせのテスト送信、未承認外部配信、規約・給与・未確認の受付条件変更は禁止。個人情報・相談本文・検索クエリ本文・認証情報をGA4/日報/GitHubへ保存しない。
GPTは成果基準・優先度・検証、Coworkは文章/保護者心理/UXと既存権限内のWP作業、Codexはコード/計測/テスト/公開確認。新規ツール購入やユーザーの中継を前提にせず、実際に利用できる実行経路で進める。
