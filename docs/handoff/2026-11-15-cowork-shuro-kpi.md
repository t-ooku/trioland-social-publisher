# 就労（B型でじるみ）の KPI を別枠で追う（2026-11-15、Cowork → Codex）

所有者の質問：「なぜ、就労のKPIは追ってないの？」→ 所有者が選んだ方針：**会社HPの中で就労を別枠にし、問い合わせの種類も分ける**。

## これまで追っていなかった理由（意図して外した記録はない。抜けていた）

1. KPI表（`dashboard/latest.json`・`/admin/kpi`）はサイトごと（会社HP・保育・放デイの3つ）の作り。就労のページは会社HPの中にあり、数字が会社HPに混ざっていた。
2. でじるみ本体のサイト `digilumi.jp` は本部（株式会社グローバルソリューション）のもの。こちらには GA4・Search Console の権限がない。**今回は対象外**。
3. 会社HPのお問い合わせ（CF7 フォーム 234）には種類の欄がない。そのため、就労の利用相談と採用や法人のお問い合わせが分かれず、就労の申込を数えられない。

## 就労の範囲（定義）

- `https://www.triocareer.jp/service/digilumi/` と、その下の6事業所のページ（`tokyooota`・`chibaabiko`・`chibaichikawa`・`tochigiutsunomiya`・`chibacyuo`・`tochigioyama`）。
- GA4 では `pagePath` が `/service/digilumi/` で始まるもの、GSC では `page` が同じ前置きのもの。
- 会社HPの数字の**内訳**として扱う。会社HPの合計に足さない（二重計上しない）。

## 基準値（既存の記録から。新しい数字は作らない）

- GSC：確定 2026-11-06〜12（PT）の `/service/digilumi/` は、表示770・クリック4・CTR 0.52%・平均順位 7.88（`docs/handoff/2026-11-15-cowork-growth-pv-ctr-cvr.md`）。
- GA4：11/08〜14 の会社HPで「でじるみ事業」のページは7PV（`docs/seo/2026-11-15-inquiry-pdca.md`）。
- 6事業所ページ別の値、就労の問い合わせ件数：**未取得**。

## Codex にやってほしいこと（既存の毎朝の日報に統合。新しい定期タスクは作らない）

1. 日報で、就労の範囲について次を取得する。期間は前日と取得可能な7日。
   - GA4：セッション（ランディングページが範囲内）、PV、アクティブユーザー（期間集計を別に取得する）。
   - GA4：範囲内のページで起きた `cta_click`（`cta_type` 別。contact・tel・line など）。
   - GSC：表示・クリック・CTR・平均順位。ページ別の上位も出す。クエリ本文は保存しない。
2. `dashboard/latest.json` に就労の内訳を足し、`/admin/kpi` に「就労（会社HPの内訳）」として出す。
   - スキーマの互換に注意する。`kpi-dashboard-check.yml` の `d.sites.length===3` などの検査も、合わせて直す。
   - 会社HPの合計とは足さない、と画面に明記する。
3. 問い合わせの種類（下の所有者の作業が終わってから）。
   - CF7 に「ご用件」（項目名 `youken`）が入ると、通知メールの件名と本文に種類が載る。
   - ただし GA4 のイベント `inquiry_submit_success` の `form_type` は `corp_form_234` のままで、種類は分からない。テーマのタグ（`tools/trio_ga4.py` の `formType`）は `kind=use|recruit` しか見ないため。
   - 種類ごとの GA4 計測は、次のテーマ版で `youken` を決まったコード（例：`shuro`・`hoiku`・`after`・`recruit`・`corp`）に変えて `form_type` に付ける。テーマのアップロードは所有者の作業。
   - それまでの就労の申込件数は**未取得**と表示する。受信側（メール）の件数を読める正規の経路ができたら、匿名の件数だけを照合する。
4. 結果は匿名の集計値だけを記録する（`docs/seo/YYYY-MM-DD-inquiry-pdca.md`・`dashboard/latest.json`・Issue #15）。名前・連絡先・相談内容は書かない。
